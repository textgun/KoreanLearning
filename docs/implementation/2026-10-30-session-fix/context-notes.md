# 컨텍스트 노트

- 사용자가 계정 전환 차단, 전환 전 개인정보 삭제와 관리자 재등록, 모집 종료 후 결과 확인을 요청했다.
- 서버 신청서·계정·관리자 권한 삭제인지 화면·로그인 정보 초기화인지 확인 질문을 보냈다. 파괴적 데이터 변경은 답변 전 진행하지 않는다.
- 계정 경계의 지연 응답 차단과 기존 신청 결과 조회는 어느 선택에서도 필요한 독립 수정이다.

## Claude 이어받기

- Codex의 미커밋 수정(admin.js 세션 버전, apply.js 계정 버전·결과 조회)을 검토했다. 새 테스트 3개는 수정 전 모두 실패하고 수정 후 통과했다.
- 추가 수정. 접수 플래그 하나로는 첫 모집 전과 모집 종료를 구분할 수 없어, 그대로면 공개 페이지에 "접수 준비 중" 배지와 "모집이 종료되어도…" 로그인 패널이 함께 뜬다. 서버 함수도 아직 배포되지 않아 로그인하면 오류가 난다. application-policy.json에 statusLookupOpen(기본 false)을 추가하고, 둘 다 false면 계정 패널을 숨긴다.
- 운영 순서. 모집 개시 때 acceptingApplications·statusLookupOpen을 모두 true로, 모집 종료 때 acceptingApplications만 false로 바꾼다.
- 검증. npm test 48/48, 서버 테스트 8/8 통과, 임시 빌드 성공. 커밋 3982665(관리자 화면), 5981c38(신청 화면).
- 남은 결정. 서버 데이터 삭제 범위(이전 계정 한 명인지, 서비스 전체인지)와 담당 학생·수업 자료 처리 기준은 사용자 답변 전이라 손대지 않았다. 운영 데이터 삭제는 Firebase 로그인이 필요해 코드 배포와 별개로 사용자 확인 후 진행한다.

## 이전 계정 정리 결정 (사용자 답변)

- 범위는 이전 계정 한 명만이다. 담당 학생·학습 기록·원격 접속 연결·단원은 새 계정으로 옮기고, 새 계정을 관리자로 지정한다.
- 삭제 대상. 이전 계정의 teacherApplications·teacherProfiles·curricula·teachers 문서와 인증 계정. sharedCurriculum은 계정에 묶이지 않아 대상이 아니다.
- 순서. 새 계정 관리자 지정 → 단원 합치기 → 학생·studentIndex 소속 변경 → 남은 학생이 없을 때만 이전 문서 삭제 → 인증 계정 삭제. 관리자 공백이 생기지 않고, 중간에 실패해도 같은 명령을 다시 실행하면 이어서 끝난다.
- 단원은 덮어쓰지 않고 합친다. 새 계정은 첫 로그인 때 샘플 단원(id 1)이 저장되므로, 같은 id면 실제로 쓰던 이전 계정 것을 남기고 새 계정에만 있는 단원은 뒤에 붙인다.
- 검증. 함수 테스트 11/11(신규 3개). 임시 설정으로 Firestore·Auth 에뮬레이터를 띄워 명령줄 미리보기·실행을 끝까지 확인했다.

## 운영 실행 방법 (사용자)

1. 새 계정이 Firebase 인증에 있어야 한다(기존 앱이나 신청 페이지에서 가입). 강사 문서가 없으면 명령이 관리자 문서를 만든다.
2. Firebase 콘솔 → 프로젝트 설정 → 서비스 계정 → 새 비공개 키 생성. 키 파일은 저장소 밖에 둔다.
3. `cd functions` 후 `GOOGLE_APPLICATION_CREDENTIALS=키파일경로 node scripts/transfer-account.js --old 이전계정@메일 --new 새계정@메일`로 미리보기를 확인한다.
4. 내용이 맞으면 같은 명령 끝에 `--confirm`을 붙여 실행한다. 새 계정으로 로그인해 학생 명단·단원·관리자 메뉴를 확인한다.
5. 작업 후 콘솔에서 사용한 서비스 계정 키를 삭제하고 내려받은 키 파일도 지운다.
